# Решение

Текущая страница определяется существующим getCurrentHack: карточка из атласа, а не встроенная карточка на странице экспериментов, категория или произвольная заметка. Перед запросом ожидаются активные записи формы и читается свежий recipe.css.

В модель передаются ID и название приёма, текущие значения полей, единицы, ограничения, варианты списка и последние шесть реплик именно этого приёма. CSS целиком и содержимое других заметок не отправляются. Локальное описание считается данными, а не инструкциями.

Отдельная structured-output схема разрешает update_parameters, ask_question, no_change и search_catalog. Изменения состоят только из variable и input; числа идут без единицы, select — из объявленных вариантов, text — буквальная строка. Все изменения проверяются общей валидацией до единственной записи через Vault.process и общую очередь с формой.

Перед записью проверяются текущая страница и точное совпадение CSS со снимком запроса. Изменение CSS, включая метаданные параметров, отклоняет устаревший ответ целиком. Никакой частичной записи. Поиск не генерирует CSS. Единственную рекомендацию можно преднастроить и применить по правилам ниже.

Для относительной команды модель выбирает умеренное изменение в допустимых границах; для максимума — объявленный max. Неизвестное числовое значение ссылки на переменную темы не угадывается: задаётся вопрос. Смысл запроса интерпретирует LLM; локальная проверка гарантирует допустимость значения, но не доказывает качество интерпретации.

Параметрический запрос не требует синхронизированного каталога. search_catalog переключает на штатный поиск; это два запроса, оба учитываются в журнале. Usage записывается до разбора ответа, поэтому расходы сохраняются при невалидном JSON, отказе в записи и устаревшем контексте.

Ответ чата содержит фактически сохранённые старые/новые значения и ссылку на карточку. Без однозначной команды применения установленные сниппеты не меняются. Публикация, миграция схемы параметров и объединение текстовых систем вне этой доработки.


## Преднастройка единственной рекомендации

Схема рекомендации расширена parameterChanges. Для обычных ответов список пуст. Для одного однозначного приёма с явно желаемыми значениями поиск возвращает рекомендацию и входные значения в том же ответе. За пределами карточки это один API-запрос. Существующий роутер на открытой карточке может сначала направить запрос в каталог; отдельный запрос к модели за значениями после поиска не выполняется.

Перед поиском локально читаются текущие recipe.css известных применимых карточек (до восьми чтений одновременно). В запрос передаются только описания параметров, а не CSS. Неаннотированные, недоступные и некорректные файлы не создают прав на преднастройку. Это позволяет использовать существующий удалённый индекс без принудительной пересинхронизации; устаревшие заявления индекса об отсутствии параметров не определяют возможности локальной формы.

Перед записью: строго одна рекомендация, ID действительно извлечён file_search, запись является применимым приёмом, путь совпадает с локальным снимком, все переменные и значения проходят общую валидацию. Затем выполняется одна запись через общую очередь и Vault.process с проверкой неизменности исходного CSS. В историю попадают фактически сохранённые до/после; установленный блок меняется только при однозначной команде применения.


## Команда отдельно от настроек

Обе схемы содержат command (show/apply/uncertain) и commandEvidence. Для apply нужна точная цитата текущего запроса; история и каталог не дают разрешения. Ask_question и search_catalog не могут одновременно применять текущий приём. No_change + apply применяет сохранённые значения. Отсутствующие поля старых ответов означают отсутствие команды.

Одна рекомендация проходит проверку извлечённого ID и применимости. После сохранения параметров общий механизм кнопок включает или обновляет блок приёма под общей блокировкой истории. Затем карточка открывается через getLeaf('tab'), openFile, revealLeaf и setActiveLeaf. Несколько рекомендаций принудительно превращаются в список без команд и изменений, даже если модель прислала их. При настройке текущей карточки новая вкладка не создаётся.

Настройка исходника и применение установленного блока — последовательные операции, не общая файловая транзакция. Ошибка после сохранения сообщает, что параметры уже сохранены; ошибка записи истории после успешного применения сообщает, что приём применён. Автотесты используют подготовленные ответы модели и не доказывают качество живой интерпретации.
