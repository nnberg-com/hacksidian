## Context

Пользователь воспринимает чат как способ изменить оформление обычными словами. Поиск CSS-приёма для штатной настройки создаёт ложное «решение не найдено». Нужно расширить исполнителя отдельным типом действий; одной инструкции модели недостаточно. Это проект будущего решения, не описание реализованной функции.

## Goals / Non-Goals

Наблюдаемый результат: «Акцентным цветом сделай зелёный» меняет акцент, оставляет пользователя на текущей странице и показывает выбранный цвет с точным значением. Начальный набор ограничен четырьмя настройками из proposal. Произвольная запись конфигурации и настройки сторонних плагинов исключены.

## Decisions

### Единый выбор действия

Предварительный поток: ввод в ConversationView → классификация намерения и выбор возможности → структурированное действие → локальная проверка → исполнитель → проверка результата → ответ в чате. Штатная настройка должна быть доступна независимо от того, вернул ли её поиск по CSS-каталогу. Приоритет штатной настройки применяется только при соответствии запросу и подтверждённой поддержке.

Точки интеграции для последующей реализации: `plugin/src/view.ts`, `main.ts` (`processFeedback` / `runFeedback`), `provider.ts`, `response.ts`, `types.ts`, `prompt.ts`, `technique-command.ts`; текущие справочные записи — `catalog.ts` (`settingEntries`). Поиск приёмов и изменение их параметров остаются самостоятельными возможностями.

### Реестр и единственный путь записи

Каждая запись реестра содержит стабильный ID, описание эффекта и области действия, тип, допустимые значения/границы, чтение текущего значения, применение, проверку обновления и восстановление. Окончательный интерфейс адаптеров выбрать после проверки механизмов Obsidian. Источник истины — фактическое состояние настроек текущего vault, а не предыдущий ответ модели или копия в поисковом индексе.

Модель возвращает только ID разрешённой операции и типизированное значение. Плагин повторно читает состояние перед записью и обрабатывает внешнее изменение без молчаливого затирания. Для неподдерживаемой версии настройка недоступна исполнителю с понятным объяснением. Не использовать прямую перезапись JSON как универсальный способ изменения настроек работающего приложения.

### Намерение и значения

Явная команда авторизует выполнение без второго подтверждения. История используется для контекста, но не как новое разрешение на запись. Просьбы объяснить/показать и отрицания сохраняют отсутствие изменений. Уточнение требуется только при существенной неоднозначности действия или значения.

Обычное название цвета не требует обязательного вопроса об оттенке: нужен воспроизводимый способ выбрать конкретный цвет и явно показать результат. Точное сопоставление названий и HEX, а также использование существующей палитры остаются открытыми решениями. Пользовательский HEX не заменяется ближайшим оттенком.

### Результат и восстановление

Сохранить предыдущее значение для восстановления конкретного изменения, не для глобального отката vault. Успех включает проверку сохранения и предусмотренного механизма обновления оформления. Если значение сохранено, но визуальное обновление не подтверждено, ответ различает эти состояния. Не объявлять перезапуск обязательным для всех настроек: определить необходимость отдельно для каждой.

Не открывать страницу приёма для выполненной штатной настройки; ответ остаётся в чате. Для цвета показать образец и HEX. Сохранить существующий учёт платных обращений, включая ошибки.

## Risks / Trade-offs

- Внутренние механизмы Obsidian могут изменяться между версиями; проверка и адаптер нужны для каждой настройки.
- Тема или сниппет может перекрывать видимый эффект сохранённого значения. Не отключать их без команды пользователя.
- Название цвета не определяет единственный оттенок; правило выбора должно быть явным и последовательным.
- Восстановление не должно затирать более позднюю ручную правку.
