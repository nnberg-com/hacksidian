## Context

Текущая реализация создаёт новый Vector Store для изменившейся ревизии и переключает `catalog.active` после успешной индексации всего набора. Это сохраняет прежний готовый индекс при сбое, но повторно индексирует неизменённые документы. Уже существуют стабильные ID, хеши документов, переиспользование Files и журнал ресурсов.

## Goals / Non-Goals

Цель: объём удалённой индексации соответствует изменениям поисковых документов, при полном охвате каталога и восстанавливаемых операциях. Состав источников и запуск обновления пользователем сохраняются. Ниже зафиксирована схема для будущей реализации; её поведение при сбоях ещё предстоит проверить.

## Decisions

- Требование фиксируется как будущий change. Код плагина на этом этапе не меняется.
- Единица сравнения — сформированный поисковый документ, а не каждый физический файл атласа.
- Первая задача реализации — проверить актуальный API добавления/замены/удаления документов и выбрать стратегию согласованности. Основная схема — обновлять существующий совместимый Vector Store; корректность переходных состояний должна быть подтверждена до внедрения.
- Если выбранный API не обеспечивает атомарное переключение, нужно явно определить период блокировки поиска и восстановление. Нельзя обещать сохранение доступности старого индекса без подтверждения выбранной схемой.

## Risks / Trade-offs

- Частичная мутация удалённого индекса может рассинхронизировать результаты и локальные метаданные; нужен устойчивый журнал и проверка завершения.
- Переименование, исчезновение записи и смена формата должны отличаться от обычного изменения содержимого.
- Удаление устаревших Files допустимо только после проверки, что они больше не используются рабочим состоянием.
- Ограничения API и согласованность удаления требуют проверки перед реализацией. Платная живая проверка выполняется только по отдельному поручению; локальные тесты используют подменённый API.

## Migration Plan

Предусмотреть переход с существующего `catalog.active` без обязательной полной переиндексации совместимого индекса. Если миграция невозможна, документировать конкретную причину и сообщить её пользователю. До внедрения плагин продолжает работать по прежнему алгоритму.

## Схема обновления каталога

1. Локально сформировать поисковые документы и сравнить `entryId → hash` с последней согласованной версией. Сохранить связь `entryId → hash → fileId` и общий `storeId`, не смешивая идентификатор приёма и версию его облачного файла.
2. Рассчитать четыре списка: новые, изменённые, удалённые, неизменённые. Хешировать нормализованное поисковое содержание, исключая время операции и другие незначимые для поиска данные.
3. При отсутствии изменений закончить без удалённых мутаций. Неизменённые документы не загружать и не прикреплять заново: одного переиспользования Files в новом Vector Store недостаточно для этой оптимизации.
4. Для обычного обновления сохранить существующий Vector Store. Новые и изменённые документы загрузить как новые Files и индексировать только их. Исходные версии и журнал сохранять до подтверждённого перехода.
5. Перед изменением состава рабочего индекса приостановить новые поисковые запросы; уже выполняющиеся завершить на согласованной версии или отменить. После готовности новых документов исключить устаревшие привязки, зафиксировать актуальную карту `entryId → fileId` и только затем возобновить поиск.
6. Удаление в Vector Store имеет eventual consistency: некоторое время поиск может вернуть старый фрагмент. Проверять результаты по актуальному `fileId`, а не только по ID приёма. Устаревший фрагмент не должен попадать в контекст ответа модели. До реализации подтвердить, что выбранный способ retrieval позволяет фильтрацию до генерации; постпроверки уже сформированного ответа недостаточно. Если это невозможно, пересмотреть границу блокировки/способ retrieval, сохранив требования согласованности.
7. После переключения очистить только ресурсы этого каталога, не используемые согласованным состоянием. Ошибка очистки оставляет журнал для повтора, не запускает новую индексацию. При неизвестном результате сетевой мутации сначала сверять состояние, а не слепо повторять создание ресурса.
8. Полный rebuild — только по причинам из спецификации; пользователь видит причину. Первый запуск индексирует весь допустимый набор.

## Прогресс и управляемое ожидание

Фазы: «Собираю документы» → «Сравниваю версии» → «Загружаю N документов» → «Индексирую N документов» → «Очищаю устаревшие ресурсы» → «Готово».

При серверной индексации показывать завершённые/ожидающие/ошибочные документы, текущую партию при пакетной обработке, прошедшее время и время последнего успешного ответа API. «Проверка состояния не отвечает» отличается от подтверждённого `in_progress`. На каждой фазе должны действовать отдельный тайм-аут запроса и общий конечный срок операции; сроки и стратегия повторов фиксируются в реализации и тестируются виртуальными часами. Кнопка отмены останавливает новые действия, сохраняет журнал и явно сообщает, если уже отправленная серверная операция могла продолжиться. Поздние ответы не должны менять отменённую локальную операцию.

## Стоимость и границы учёта

В текущем пути индексации не вызываются Responses/чат-модель и отдельный Embeddings API. Обработка embeddings выполняется управляемым Vector Store. По тарифам, проверенным 2026-09-16, хранение фрагментов и embeddings оплачивается по размеру: до 1 ГБ суммарно по хранилищам бесплатно, далее $0.10/ГБ/день. File Search в Responses оплачивается отдельно: $2.50 за 1000 вызовов; используемые моделью токены оплачиваются по её тарифу. Это три разных показателя; оценка токенов текста не является счётом за индексацию.

Нельзя обещать бесплатность конкретному пользователю, зная только размер одного каталога: неизвестно использование общей бесплатной квоты. Размер файлов на диске также не равен размеру индекса. Оптимизация прежде всего сокращает ожидание, сетевые операции и дублирование облачного хранения. Тарифы следует перепроверить перед реализацией; неизвестные расходы не показывать как подтверждённый ноль.
