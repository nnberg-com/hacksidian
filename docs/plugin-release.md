# Выпуск плагина

Плагин и контент обновляются независимо. Выпуск плагина содержит только `main.js`, `styles.css` и `manifest.json`. Атлас и песочница не входят в пакет; пользователь обновляет их отдельно в локальном Git-репозитории.

Для установки у пользователя должны быть локальная копия этого репозитория с `content/atlas` и `content/playground`, Node.js 22 или новее и выбранный существующий vault вне репозитория. Материалы подключаются через символические ссылки по путям из настроек `atlasFolder` и `coloringsFolder`: пути в настройках менять не требуется. При первой установке используются `Hacksidian/atlas` и `Hacksidian/playground`. Ссылки ведут в тот репозиторий, из которого запущен установщик.

Оба режима установки — из исходников и из скачанного релиза — создают недостающие ссылки и сохраняют существующие правильные ссылки. Обычная папка или ссылка на другой источник на месте назначения останавливает установку до изменения плагина. Материалы автоматически не удаляются и не переносятся. Уже скопированный контент требует отдельного согласованного переноса перед переходом на ссылки.

## Подготовка версии

Из корня репозитория:

```sh
npm --prefix plugin run release:version -- 0.1.0
npm --prefix plugin run release:prepare
```

`0.1.0` — пример; для следующего выпуска выбирайте новый номер `X.Y.Z`. Команда версии обновляет корневой и внутренний manifest, package.json и обе записи версии в package-lock.json. Она не создаёт коммитов и тегов. Версия vault независима.

`release:prepare` проверяет типы, собирает код, запускает тесты и заново создаёт `build/release/` ровно с тремя файлами. Расхождения manifest и версий останавливают упаковку. Атлас, песочница и пользовательские данные туда не копируются.

Добавьте `docs/plugin-releases/X.Y.Z.md`: изменения поведения, минимальную версию Obsidian, известные ограничения совместимости с контентом и инструкции обновления. Для `0.1.0` описание уже подготовлено. Если новая версия требует другого формата контента, это нужно явно указать; автоматическая доставка контента не выполняется.

## Черновик и публикация

1. Проверьте diff, зафиксируйте и отправьте изменения в GitHub.
2. Создайте тег на подготовленном коммите и отправьте его:

   ```sh
   git tag 0.1.0
   git push origin 0.1.0
   ```

3. Дождитесь workflow `Build plugin`. Тег должен точно совпадать с версией manifest, без `v`. Workflow проверяет наличие описания выпуска и создаёт **черновик** `Hacksidian plugin X.Y.Z` с тремя файлами. Push в main, pull request и ручной запуск на ветке создают только Actions artifact. Теги `vault-*` обслуживает отдельный workflow.
4. Скачайте файлы именно из черновика. Проверьте новую установку и обновление в отдельном тестовом vault в настольном Obsidian: загрузку плагина, панель, работу с имеющимися материалами, сохранность настроек, истории и пользовательского CSS. Не запускайте платные API-проверки без отдельного решения.
5. После проверки опубликуйте черновик в GitHub.

Повторный запуск создания уже существующего релиза завершится ошибкой, не заменяя его вложения. Для исправления опубликованного выпуска используйте новую версию. Автоматические архивы `Source code` не являются готовым плагином.

## Установка и обновление пользователем

1. Закройте Obsidian. Перед обновлением сохраните резервную копию текущей папки плагина.
2. Скачайте `main.js`, `styles.css`, `manifest.json` из одного выпуска в отдельную папку.
3. Из корня локального репозитория выполните:

   ```sh
   HACKSIDIAN_VAULT="/absolute/path/to/vault" npm --prefix plugin run install:release -- "/absolute/path/to/downloaded-release"
   ```

4. Откройте Obsidian: плагин включён, атлас и песочница доступны через ссылки.

Команда не требует `npm ci`, не пересобирает плагин и не выполняет Git-команды. Она устанавливает три скачанных файла, сохраняя существующие настройки и историю в `data.json`, пользовательские CSS-сниппеты и остальные файлы. Старый неиспользуемый `content.json.gz` удаляется. Для нестандартной папки конфигурации задайте `HACKSIDIAN_CONFIG_DIR` вместо `.obsidian`.

Обновление плагина выполняется той же командой. Оно не делает `git pull`, не изменяет материалы и пути в настройках. Обновление файлов в локальном репозитории сразу видно через ссылки. Не переносите репозиторий без перенастройки ссылок. Правки материалов через Obsidian меняют файлы репозитория.

Для отката кода при закрытом Obsidian используйте эту же команду с тремя файлами предыдущего выпуска. Если выпуск меняет формат пользовательских данных, следуйте его инструкции отката и используйте резервную копию.

`install:vault` собирает плагин из исходников перед установкой; `install:release` берёт готовые файлы из указанной папки. Оба используют материалы локального репозитория. Включение в каталог Community Plugins и автоматическое обновление через него не входят в этот процесс.

## Проверки

```sh
npm --prefix plugin run release:prepare
python3 -m unittest discover -s tools/tests -p 'test_*vault*.py' -v
```

Тесты установки из релиза проверяют создание ссылок, повторное обновление, сохранность настроек, истории и CSS, отказ при конфликтах и неполном пакете. Тесты упаковщика используют временные каталоги: проверяют версии, теги, исключение посторонних файлов и поведение при неполной сборке. Проверки скриптов не заменяют проверку скачанного релиза в Obsidian.
