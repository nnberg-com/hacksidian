# Код внутри длинного технического текста

## Эта раскраска нужна для настройки чтения статьи, в которой обычная проза постоянно сменяется фрагментами кода на нескольких языках.

Хороший кодовый блок должен заметно отличаться от абзаца, но не выпадать из общего ритма статьи. Читатель должен без усилий находить начало и конец примера, различать комментарии, строки, числа и ключевые слова, а затем спокойно возвращаться к обычному тексту. Ниже одна небольшая задача показана на пяти языках, чтобы оформление можно было оценить на реальном наборе конструкций.

### C: данные, указатели и явные границы

В C особенно хорошо видны препроцессорные директивы, типы, числовые константы, указатели и функции стандартной библиотеки. Этот пример накапливает значения датчика и печатает среднее. Здесь есть многострочная сигнатура, ранний выход, форматная строка и комментарий — достаточно разные элементы для проверки контраста.

```c
#include <stdio.h>
#include <stddef.h>

#define SAMPLE_LIMIT 8

typedef struct {
    const char *name;
    double values[SAMPLE_LIMIT];
    size_t count;
} SensorSeries;

static double average(const SensorSeries *series) {
    if (series == NULL || series->count == 0) {
        return 0.0;
    }

    double total = 0.0;
    for (size_t i = 0; i < series->count; ++i) {
        total += series->values[i];
    }
    return total / (double)series->count;
}

int main(void) {
    SensorSeries room = {
        .name = "studio",
        .values = {21.4, 21.8, 22.1, 21.9},
        .count = 4,
    };

    /* Keep the unit next to the value in human-readable output. */
    printf("%s: %.1f °C\n", room.name, average(&room));
    return 0;
}
```

После плотного блока полезно проверить возвращение к пропорциональному шрифту. Если фон слишком тяжёлый, код перетягивает на себя всю страницу; если граница почти не видна, пример сливается с соседними абзацами. Отдельного внимания требует строка `average(&room)`: inline code должен быть родственен большому блоку, но не превращать строку текста в череду плашек.

### Bash: команды, переменные и поток вывода

Shell-сценарий создаёт другой рисунок. В нём много служебных знаков, кавычек, подстановок, коротких команд и длинных аргументов. Подсветка должна помогать различать структуру, не делая знаки `$`, `{}` и `[]` ярче содержательных частей.

```bash
#!/usr/bin/env bash
set -euo pipefail

readonly SOURCE_DIR="${1:-./samples}"
readonly REPORT_FILE="${2:-./build/report.tsv}"

collect_reports() {
  local file
  mkdir -p "$(dirname "$REPORT_FILE")"
  : > "$REPORT_FILE"

  while IFS= read -r -d '' file; do
    printf '%s\t%s\n' \
      "$(basename "$file")" \
      "$(wc -l < "$file" | tr -d ' ')" \
      >> "$REPORT_FILE"
  done < <(find "$SOURCE_DIR" -type f -name '*.log' -print0)
}

if [[ ! -d "$SOURCE_DIR" ]]; then
  printf 'Directory not found: %s\n' "$SOURCE_DIR" >&2
  exit 1
fi

collect_reports
printf 'Saved %s\n' "$REPORT_FILE"
```

У Bash-блока стоит посмотреть на перенос длинной команды и на то, не теряются ли кавычки рядом с переменными. В технической статье вокруг такого примера обычно встречаются короткие команды вроде `chmod +x report.sh` и имена файлов вроде `report.tsv`; поэтому их вид внутри строки тоже входит в общую композицию.

### Python: типы, строки и выражения

Python даёт больше воздуха благодаря отступам, но длинные аннотации типов и форматированные строки быстро возвращают визуальную плотность. В примере есть декоратор, `None`, генераторное выражение, исключение и f-строка. Комментарий намеренно находится между рабочими строками, а не вынесен в отдельную шапку.

```python
from dataclasses import dataclass
from statistics import fmean
from typing import Iterable


@dataclass(frozen=True, slots=True)
class Reading:
    sensor: str
    value: float
    unit: str = "°C"


def summarize(readings: Iterable[Reading]) -> dict[str, float]:
    grouped: dict[str, list[float]] = {}
    for reading in readings:
        grouped.setdefault(reading.sensor, []).append(reading.value)

    if not grouped:
        raise ValueError("at least one reading is required")

    # Round only the value shown to a person; preserve source precision.
    return {
        sensor: round(fmean(values), 1)
        for sensor, values in grouped.items()
    }


summary = summarize([
    Reading("studio", 21.4),
    Reading("studio", 21.8),
    Reading("kitchen", 23.05),
])
print(f"Studio average: {summary['studio']:.1f} °C")
```

Если комментарий становится почти невидимым, читать объясняющий код трудно; если он слишком насыщенный, комментарии начинают конкурировать с исполняемыми строками. Строки и числа тоже должны отличаться друг от друга без ощущения праздничной гирлянды. Это особенно заметно рядом с обычным абзацем, где используются *курсив*, **сильное выделение** и ссылка на [описание синтаксиса](https://help.obsidian.md/syntax).

### JavaScript: объекты и асинхронная работа

В JavaScript полезно проверить стрелочные функции, шаблонные строки, optional chaining и `async`/`await`. Код ниже получает уже существующий JSON-ответ, отбрасывает некорректные записи и строит удобные для интерфейса подписи. Это типичный прикладной фрагмент, а не искусственный перечень токенов.

```javascript
const endpoint = new URL("/api/readings", window.location.origin);
endpoint.searchParams.set("room", "studio");

async function loadReadings(signal) {
  const response = await fetch(endpoint, {
    headers: { Accept: "application/json" },
    signal,
  });

  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }

  const payload = await response.json();
  return payload.items
    .filter((item) => Number.isFinite(item?.value))
    .map(({ sensor, value, unit = "°C" }) => ({
      id: crypto.randomUUID(),
      label: `${sensor}: ${value.toFixed(1)} ${unit}`,
    }));
}

const controller = new AbortController();
loadReadings(controller.signal)
  .then((items) => console.table(items))
  .catch((error) => console.error("Could not load readings", error));
```

В этом блоке особенно много пунктуации. Скобки и запятые не обязаны быть акцентами, однако должны оставаться различимыми на выбранном фоне. Проверить стоит и горизонтальное поведение: строка с обработчиком ошибки достаточно длинная, но не настолько, чтобы сама по себе диктовать ширину всей статьи.

### TypeScript: типы как второй голос

TypeScript добавляет слой, которого нет в JavaScript: типы читаются вместе с программой, но выполняют другую роль. Если подсветка делает их слишком бледными, теряется смысл примера; если слишком яркими — основная логика отступает назад. Здесь используются литеральные объединения, интерфейс, обобщённый тип, проверка вариантов и оператор `satisfies`.

```typescript
type Unit = "°C" | "%";

interface Reading<TUnit extends Unit = Unit> {
  sensor: string;
  value: number;
  unit: TUnit;
  capturedAt: Date;
}

type LoadState<T> =
  | { status: "idle" }
  | { status: "loading"; startedAt: number }
  | { status: "ready"; data: readonly T[] }
  | { status: "failed"; error: Error };

function describeState<T>(state: LoadState<T>): string {
  switch (state.status) {
    case "idle":
      return "No request yet";
    case "loading":
      return `Loading for ${Date.now() - state.startedAt} ms`;
    case "ready":
      return `${state.data.length} readings available`;
    case "failed":
      return state.error.message;
  }
}

const current = {
  status: "ready",
  data: [{
    sensor: "studio",
    value: 21.8,
    unit: "°C",
    capturedAt: new Date("2026-09-03T12:00:00Z"),
  }],
} satisfies LoadState<Reading<"°C">>;

console.info(describeState(current));
```

После пяти примеров уже можно оценивать систему целиком. Достаточно ли заметно имя языка, если интерфейс его показывает? Нужна ли рамка? Должны ли блоки иметь прямые или скруглённые углы? Удобно ли выделять код мышью? Не выглядит ли вертикальный отступ перед примером случайно больше, чем отступ после него?

### Возвращение к обычному чтению

Техническая статья остаётся статьёй, даже когда кода в ней много. Финальный фрагмент снова собран из обычных предложений, чтобы после цветных токенов можно было почувствовать спокойствие или, наоборот, недостаток визуальной связи. Кодовые блоки здесь выступают крупными объектами внутри текста, а не отдельной галереей образцов.

Итоговая раскраска считается удачной, если взгляд легко переключается между объяснением и реализацией: заголовок задаёт тему, абзац формирует ожидание, блок позволяет рассмотреть детали, а следующая фраза возвращает нить рассуждения. Любой из примеров можно отредактировать как обычный Markdown-документ; CallMeRed должен работать с тем, что пользователь действительно оставил на странице.
