## Системные проблемы и предлагаемые исправления

### 1. Полный CSS является единицей каждой итерации

Системный prompt требует от модели при каждом `update_css` возвращать полный replacement stylesheet. Формально он также требует сохранять всё, на что пользователь не жаловался. На практике размер контекста и локальный характер запроса привели к потере компонентов.

История не решает проблему: она позволяет вручную найти старое состояние, но не позволяет безопасно собрать принятые решения разных итераций.

#### Предложение

Внутренне хранить стиль как набор независимых машинных модулей:

1. `tokens`: палитра, типографика, размеры, интервалы, радиусы.
2. `page`: фон, ширина текста, поля, поведение viewport.
3. `typography`: основной текст, H1, H2-intro, H3–H6.
4. `links-and-inline`: ссылки, external link, unresolved link, tag, mark, inline code.
5. `lists`: bullets, numbering, nesting, task list.
6. `quotes-and-callouts`: blockquote и пять поддерживаемых callout-типов.
7. `tables`.
8. `code`: code block и syntax tokens.
9. `media`: изображения и embeds.
10. `math-and-footnotes`.
11. `mermaid`.
12. `obsidian-integration`: только необходимые адаптационные селекторы и `!important`.

Пользователь не обязан видеть или обсуждать эти категории. Это внутреннее устройство, которое защищает его уже выраженные предпочтения.

LLM должна возвращать изменение конкретного модуля или структурированное описание дельты. Полный активный CSS затем детерминированно собирается программой.

### 2. Нет машинного контракта сохранности решений

Сейчас prompt просит модель «сохранить детали», но приложение не проверяет результат. Валидатор проверяет синтаксис, область действия, запрещённые URL, `display:none`, `visibility:hidden`, shorthand `font` и разрешённые шрифты. Он не проверяет, сохранились ли списки, выноски, таблицы и сноски.

#### Предложение

Для каждого модуля хранить небольшой структурный контракт:

- обязательные переменные;
- обязательные группы селекторов;
- поддерживаемые состояния;
- компоненты, которые разрешено изменить текущей операцией;
- компоненты, которые должны остаться эквивалентными предыдущей версии.

При запросе про код новая версия не должна приниматься, если из неё исчезли селекторы callout, footnotes или task list.

Дополнительный сигнал регрессии — аномальное сокращение CSS. Падение с 24 500 до 11 727 байт после локального запроса должно требовать повторной генерации или локального восстановления, а не немедленного применения.

### 3. Смешаны исходная палитра, семантика и конкретные компоненты

В одном блоке переменных сейчас находятся три разных вида сущностей.

Исходные пользовательские цвета:

- `--cmr-blue`;
- `--cmr-cyan`;
- `--cmr-green`;
- `--cmr-purple`;
- `--cmr-brown`;
- `--cmr-red`;
- `--cmr-orange`;
- `--cmr-yellow`.

Семантические роли:

- `--cmr-text`;
- `--cmr-rule`;
- `--cmr-quote`;
- `--cmr-unresolved-link`.

Компонентные значения:

- `--cmr-h2`;
- `--cmr-code-block-bg`;
- `--cmr-code-text`;
- `--cmr-footnote-highlight`;
- `--cmr-callout-note` и остальные callout-переменные из полной версии.

Из-за этого некоторые правила используют сырой цвет напрямую, другие — роль, третьи — компонентный alias. Непонятно, должна ли смена `green` одновременно менять inline code, TIP, комментарии и строки в коде.

#### Предложение

Сохранить все точные выбранные пользователем цвета и добавить поверх них два внутренних уровня.

Уровень 1 — исходные цвета:

```css
--cmr-color-cyan: #08849b;
--cmr-color-green: #9a9a00;
--cmr-color-purple: #7c33de;
```

Уровень 2 — роли:

```css
--cmr-text-primary: var(--cmr-color-ink);
--cmr-link-default: var(--cmr-color-cyan);
--cmr-accent-positive: var(--cmr-color-green);
```

Уровень 3 — компоненты:

```css
--cmr-callout-tip-title: var(--cmr-accent-positive);
--cmr-syntax-comment: var(--cmr-accent-positive);
```

Это не текстовый вывод о стиле и не попытка истолковать пользователя. Это система ссылок между зафиксированными решениями. Она позволяет позднее разъединить два применения цвета без потери исходного факта.

### 4. Объявленные типографические переменные обходятся прямыми значениями

В корневом scope определены `--font-text`, `--font-interface` и `--font-monospace`, но ниже `Onest` и `MesloLGS Nerd Font Mono` многократно записываются напрямую.

Так же повторяются:

- `font-size: 18px`;
- `line-height: 1.5`;
- семейство Onest для основного текста;
- семейство Meslo для code, tag и mark.

Это создаёт несколько независимых источников истины. Изменение переменной не гарантирует смену всех компонентов.

#### Предложение

Определить собственные переменные:

- `--cmr-font-text`;
- `--cmr-font-code`;
- `--cmr-text-size`;
- `--cmr-line-height-body`;
- `--cmr-line-height-heading`;
- `--cmr-line-height-intro`;
- `--cmr-line-height-code`.

Затем через них задавать как CSS CallMeRed, так и совместимые документированные переменные Obsidian. Прямые названия шрифтов должны оставаться только в одном месте.

### 5. Типографическая шкала не описывает собственное правило

Текущие размеры:

- H1 — 64,5 px;
- H2 — 24 px;
- H3 — 42 px;
- H4 — 36 px;
- H5 — 31,5 px;
- H6 — 27,75 px;
- основной текст — 18 px.

H2 намеренно исключён из обычной иерархии: он выполняет функцию intro и поэтому меньше H3. Это принятое продуктовое решение, его нужно сохранить.

Но H3–H6 не имеют явной общей пропорции. Общая группа заголовков задаёт `line-height: 1.12`, после чего H3–H6 переопределяют его как `calc(1em + Npx)`. Фактический коэффициент для них получается около 1,24–1,25.

#### Предложение

Не пересчитывать автоматически уже выбранные кегли. Сначала зафиксировать их как принятые значения. Затем описать четыре отдельных типографических режима:

- display для H1;
- intro для H2;
- section headings для H3–H6;
- body для текста.

Для line-height использовать безразмерные коэффициенты. Тогда изменение кегля не будет непредсказуемо менять внутренний зазор в пикселях.

Отдельно на типографической раскраске нужно проверить, действительно ли H3–H6 должны иметь один line-height или пользователь предпочитает разные значения.

### 6. Вертикальный ритм построен из частных исключений

В CSS есть отдельные решения для:

- H2 перед абзацем;
- H3, H4, H5 и H6 перед абзацем;
- абзаца перед абзацем;
- блока кода перед H4;
- в полной версии — текста перед списком и заголовка перед несколькими видами контента.

При этом нет общей модели для сочетаний:

- заголовок → таблица;
- заголовок → диаграмма;
- заголовок → формула;
- список → абзац;
- цитата → следующий раздел;
- выноска → следующий раздел;
- изображение → подпись или абзац;
- таблица → следующий заголовок.

Исключение `pre + h4` особенно хрупкое: нужный интервал зависит не от уровня следующего заголовка, а от того, что перед ним оказался code block.

#### Предложение

Ввести небольшой набор интервальных ролей:

- расстояние между строками внутри элемента;
- расстояние между абзацами;
- расстояние между текстом и связанным с ним модулем;
- расстояние между самостоятельными модулями;
- расстояние перед новым разделом;
- внутренние поля компонента.

Затем проверить матрицу переходов на всех специализированных раскрасках. Не нужно делать все расстояния одинаковыми; нужно, чтобы каждое различие было осознанным и повторяемым.

### 7. Поля всей статьи зависят от размера иконки выноски

В полной версии:

```css
--cmr-callout-icon-size: 40px;
--cmr-callout-icon-side: 16px;
--cmr-page-margin: calc(var(--cmr-callout-icon-size) + var(--cmr-callout-icon-side) * 2);
```

Изменение иконки NOTE, TIP или WARNING автоматически меняет поля всей статьи. Это неправильная зависимость между компонентом и layout.

#### Предложение

Разделить четыре независимых величины:

- gutter страницы;
- ширину зоны для элементов, висящих на полях;
- размер callout-иконки;
- промежуток между иконкой и текстом.

Выноска может использовать поле страницы, но не должна определять его.

### 8. Поля заданы на прокручиваемом контейнере

Текущий CSS задаёт `padding-inline-start` и `padding-inline-end` непосредственно `.markdown-preview-view.callmered-coloring`.

На последнем скриншоте виден горизонтальный scrollbar. Наиболее вероятная причина — padding увеличивает ширину самого прокручиваемого viewport.

#### Предложение

Ширину текста и gutter следует задавать внутреннему контентному контейнеру Obsidian, а не scroll viewport. Нужны:

- `box-sizing: border-box`;
- ограничение ширины строки;
- адаптивные поля через `clamp()` или эквивалентную схему;
- проверка на узком и широком окне;
- отдельная проверка элементов, вынесенных на поля.

Используемые DOM-классы Obsidian должны считаться версионно-зависимым интеграционным слоем, а не ядром стилевой системы.

### 9. Система радиусов зависит от внешней переменной Obsidian

Сейчас:

```css
--cmr-inline-radius: var(--radius-l);
```

Теги, inline code, code blocks и изображения используют это значение. Поэтому принятая пользователем геометрия зависит от значения `--radius-l` в текущей версии Obsidian или активной теме.

В предыдущей версии параллельно существовал `--cmr-radius: 4px`, что создавало уже две шкалы без явно описанного отношения.

#### Предложение

Зафиксировать собственные значения CallMeRed:

- базовый радиус 4 px;
- увеличенный радиус 8 px для тех inline-элементов, где было принято удвоение;
- при необходимости отдельный радиус для больших поверхностей.

Связь «увеличенный равен двум базовым» должна быть видна в машинной структуре. Переменная Obsidian может получать значение из CallMeRed, но не наоборот.

### 10. Общая геометрия случайно объединяет типографику разных элементов

Текущий групповой селектор объединяет:

- inline code;
- `mark`;
- tag.

Вместе с padding, margin и radius он назначает всем трём MesloLGS Nerd Font Mono. В результате обычное Markdown-выделение `==текст==` становится моноширинным.

Возможно, визуально это понравится пользователю. Однако отдельного факта-реакции, подтверждающего именно моноширинный `mark`, в исследованной последовательности нет. Похоже, типографика попала туда как побочный эффект объединения геометрии.

#### Предложение

Сохранить общие geometry tokens для компактных плашек, но разделить:

- семейство шрифта;
- цвет текста;
- цвет фона;
- интерактивные состояния.

Раскраска должна позволить отдельно увидеть mark, tag и inline code в обычном тексте и внутри заголовка.

### 11. Одинаковые hex-цвета на светлой и тёмной поверхности дают очень разную читаемость

Были рассчитаны контрастные отношения основных сочетаний:

| Сочетание | Контраст |
|---|---:|
| `#110f00` на белом | 19,23:1 |
| cyan `#08849b` на белом | 4,39:1 |
| unresolved link `#3fb3cd` на белом | 2,46:1 |
| quote `#817f6f` на белом | 4,04:1 |
| H2/rule `#b0ae9c` на белом | 2,24:1 |
| кремовый текст `#fefbe5` на green `#9a9a00` | 2,88:1 |
| основной текст на yellow `#f3ac06` | 9,81:1 |
| основной кремовый текст на code background `#2b291f` | 13,99:1 |
| green syntax на code background | 4,86:1 |
| yellow syntax на code background | 7,44:1 |
| purple syntax на code background | 2,35:1 |
| red syntax на code background | 1,69:1 |

Это не означает, что пользовательские цвета «неправильные». Выявлен конфликт применений:

- красный и фиолетовый хорошо работают как акценты на светлом фоне;
- те же точные hex-коды становятся плохо различимы на тёмном code background;
- светло-серые значения могут работать как декоративные линии, но становятся слабыми для информативного текста.

#### Предложение

Сохранить исходную именованную палитру без изменений. Добавить варианты для конкретных поверхностей:

- `purple-on-light` и `purple-on-dark`;
- `red-on-light` и `red-on-dark`;
- при необходимости отдельный цвет вторичного текста и отдельный цвет декоративной линии.

Варианты на тёмном фоне должны сохранять узнаваемый оттенок, но иметь другую светлоту. Это предложение обязательно нужно показать пользователю на раскраске кода, а не принимать только по числам.

Если требование использовать буквально один и тот же hex важнее читаемости, система должна зафиксировать этот выбор как намеренный конфликт, а не незаметно корректировать цвет.

### 12. Интерактивные состояния не образуют явной системы

Обычная ссылка и ссылка при hover используют одинаковый cyan. Это может быть правильным пользовательским решением, но сейчас непонятно, является ли оно осознанным или просто осталось по умолчанию.

Не зафиксированы как единая система:

- hover;
- keyboard focus;
- visited;
- active и target;
- unresolved;
- checked и disabled;
- раскрытая и закрытая выноска;
- интерактивная строка таблицы, если она появится позднее.

#### Предложение

Для каждого интерактивного компонента хранить таблицу состояний. Состояния не обязаны визуально различаться цветом: одинаковое отображение тоже допустимо, если оно принято после показа.

Особенно важно отдельно проверить keyboard focus. Он функционален и не должен исчезнуть из-за общего сброса фона, outline или decoration.

### 13. External-link icon является отдельным мелким цветовым элементом

Стандартная иконка Obsidian заменена текстовым символом `↗`. Ему назначен `#9a9a9a`, размер `0.78em` и вертикальный сдвиг `top: -1px`.

Контраст этого серого на белом — около 2,81:1. Символ мал и может выглядеть слабее связанного с ним цианового текста. Положение также зависит от метрик текущего шрифта.

#### Предложение

Отдельно показать несколько ссылок на раскраске:

- внутри обычного текста;
- в заголовке;
- в списке;
- рядом со знаками препинания;
- в многострочной ссылке.

Если существующий вид нравится, зафиксировать размер и offset как компонентные значения. Если символ кажется случайным, подобрать его геометрию визуально, не исходя только из CSS-метрик.

### 14. `text-muted` приравнен к основному тексту, а вторичные состояния восстанавливаются вручную

В scope задано:

```css
--text-normal: var(--cmr-text);
--text-muted: var(--cmr-text);
```

Это убирает стандартную семантическую разницу Obsidian целиком. Затем H2, сноски, выполненные задачи и другие элементы получают собственные цвета отдельными правилами.

Такой подход легко пропускает новые вторичные элементы: они внезапно оказываются основного цвета.

#### Предложение

Определить отдельный семантический `--cmr-text-muted`, даже если первоначально он совпадает с основным текстом. Компоненты должны ссылаться на роль, а не предполагать, что глобальная переменная Obsidian всегда подходит.

### 15. Синтаксическая палитра задаётся двумя параллельными механизмами

Текущий файл одновременно:

1. Переопределяет Obsidian-переменные `--code-*`.
2. Явно окрашивает классы Prism `.token.*` и Highlight.js `.hljs-*`.

Это повышает вероятность расхождения: новый тип токена может получить цвет через один механизм, а старый — через другой.

Кроме того, несколько семантически разных конструкций объединены одним цветом:

- строки и комментарии — green;
- числа, boolean, функции, классы, встроенные типы, параметры — yellow;
- keywords, properties и attributes — purple;
- удалённый текст, regex, tags и meta — red.

Такое укрупнение может быть подходящим стилем, но должно проверяться не только на одном языке. Раскраска уже содержит C, Bash, Python, JavaScript и TypeScript, поэтому можно проверить, не становится ли один из языков почти одноцветным.

#### Предложение

Сделать собственные semantic syntax tokens единым источником истины, а оба механизма интеграции направить на них. Например:

- syntax-comment;
- syntax-string;
- syntax-keyword;
- syntax-name;
- syntax-number;
- syntax-punctuation;
- syntax-error-or-deletion.

Пользователь по-прежнему оценивает только картинку. Эти категории нужны машине для сохранения согласованности разных языков.

### 16. Набор раскрасок опережает фактическое покрытие CSS

Даже предыдущая полная версия почти не оформляет некоторые уже существующие раскраски.

#### Mermaid

Нет отдельной системы для:

- canvas диаграммы;
- текста;
- узлов и кластеров;
- линий и стрелок;
- подписей осей;
- легенд;
- разных состояний;
- Gantt, Sankey, mindmap, quadrant, timeline, GitGraph и других разных по устройству диаграмм.

В результате Mermaid продолжает жить в собственной стандартной теме и не обязательно соответствует статье.

#### Формулы

Нет явных правил для:

- inline math;
- display math;
- расстояний до соседнего текста;
- размера и цвета формул;
- переполнения длинных выражений.

#### Таблицы

В полной версии заданы в основном внешние отступы и border radius. Не зафиксированы:

- header cells;
- границы;
- выравнивание;
- числовые столбцы;
- zebra или её отсутствие;
- широкие таблицы;
- перенос текста;
- поведение на узком viewport.

#### Изображения

Для них зафиксирован только radius. Не определены:

- максимальная ширина;
- выравнивание;
- вертикальные интервалы;
- подпись;
- embeds;
- поведение очень маленького и очень широкого изображения.

#### Предложение

Продолжать груминг через специализированные раскраски, но после каждой из них обновлять только соответствующий модуль. Обзорная «Длинная статья» должна использоваться как интеграционный тест: все базовые элементы обязаны сохранять общий ритм в одном тексте.

### 17. Специализированные CSS-классы раскрасок пока не используются как контекст проверки

Документы имеют классы `callmered-code`, `callmered-lists`, `callmered-mermaid` и другие, однако активный CSS в основном использует только общий `.callmered-coloring`.

Для итогового личного стиля это логично: компонент должен выглядеть одинаково в любой статье. Но специализированные классы полезны для двух служебных задач:

- добавить исключительно контрольную разметку раскраски, не перенося её в обычные документы;
- ограничить временный эксперимент до принятия решения пользователем.

#### Предложение

Разделить:

- итоговые глобальные компонентные правила под `.callmered-coloring`;
- временные или диагностические правила конкретной раскраски под её дополнительным классом.

После принятия решения диагностическая часть должна исчезать, а итоговое правило — переходить в соответствующий глобальный модуль.

### 18. Избыточное использование `!important` делает собственный каскад жёстким

В текущей версии `!important` используется в 57,1% деклараций, в предыдущей полной — в 60,8%.

В Obsidian часть усилений действительно необходима из-за существующей темы и специфичности app CSS. Но при таком объёме:

- компоненты плохо наследуют общие решения;
- локальные исключения требуют ещё более точных селекторов;
- становится трудно понять, какое правило является источником истины;
- смена DOM или версии Obsidian увеличивает риск поломок.

#### Предложение

Разделить stylesheet на два логических слоя:

1. Внутренняя система CallMeRed с нормальным каскадом и минимумом `!important`.
2. Узкий адаптер Obsidian, где усиление разрешено только против конкретно подтверждённого правила приложения.

Каждый `!important` желательно связывать с причиной: какой стандартный селектор Obsidian он перебивает. Это можно хранить в комментарии или тесте, не показывая пользователю.

### 19. Использование DOM-классов Obsidian местами дублируется

Для одного визуального отношения CSS часто пытается покрыть одновременно:

- непосредственную структуру `h2 + p`;
- wrapper-структуру `.el-h2 + .el-p`;
- селекторы с `:has()`.

Это появилось из реальной необходимости: несколько первых попыток изменить расстояние под H2 визуально не сработали. Однако результат стал хрупким и трудным для дальнейшего изменения.

#### Предложение

После того как рабочий DOM-путь подтверждён в текущей версии Obsidian, оставить минимальный набор действительно необходимых селекторов. Версионно-зависимые `.el-*` правила держать в интеграционном модуле и проверять скриншотными сценариями.

Нельзя считать все переменные и классы, найденные внутри установленного `app.css`, вечным публичным API Obsidian. Они являются свидетельством конкретной установленной версии.

### 20. H2-intro следует закрепить как отдельный контракт документа

В текущей системе H2 — не обычный второй уровень иерархии, а intro после H1. Внутренние заголовки начинаются с H3. Это важное принятое решение.

Сейчас CSS просто стилизует любой H2 как intro. Если пользователь случайно добавит второй H2 в середине документа, он тоже станет intro с двумя линиями.

#### Предложение

На уровне раскрасок и будущих документов явно закрепить контракт:

- один H1 на страницу;
- не более одного H2;
- H2 расположен непосредственно в вводной части;
- внутренние разделы используют H3–H6.

Поскольку документы доступны для ручного редактирования, система должна обнаруживать нарушение и сообщать его как потерю контрольного условия. Не нужно автоматически переписывать пользовательский Markdown.

## Что уже сделано системно удачно

Важно не потерять сильные стороны при реорганизации.

### Область действия ограничена раскрасками

Все основные правила требуют `.markdown-preview-view.callmered-coloring`. Стиль не применяется ко всему vault и не затрагивает панель разговора.

### Пользовательская палитра уже вынесена в переменные

Несмотря на смешение уровней, точные выбранные цвета собраны в начале файла. Это хорошая исходная точка для трёхслойной системы токенов.

### H2 действительно отделён от обычной иерархии

Его роль intro выражена цветом, весом, размером, line-height и двумя горизонтальными линиями. Это не случайная вариация H3.

### Код имеет собственную поверхность и шрифт

Тёмный фон, светлый основной текст и Meslo образуют отчётливый режим, который можно систематизировать, не пересматривая его основу.

### История сохраняет фактические CSS-состояния и скриншоты

Благодаря этому потерянные решения можно восстановить точно, а не по текстовому пересказу. Для системы, основанной на визуальных реакциях, это принципиально правильно.

### Применяется parser-based валидация CSS

CSS уже разбирается PostCSS, поэтому структурные проверки можно расширять без ненадёжного разбора регулярными выражениями.

## Предлагаемая целевая структура стилевой системы

Ниже не предлагается показывать пользователю формальное описание его стиля. Это схема внутреннего хранения и сборки.

```text
Факты
├── точный Markdown раскраски
├── снимок до изменения
├── дословная реакция пользователя
├── снимок после изменения
└── принятая CSS-дельта

Стилевая система
├── raw tokens
│   ├── точные цвета
│   ├── шрифты
│   └── числовые величины
├── semantic tokens
│   ├── текстовые роли
│   ├── поверхности
│   ├── акценты
│   └── интервальные роли
├── component modules
│   ├── typography
│   ├── links
│   ├── lists
│   ├── callouts
│   ├── tables
│   ├── code
│   ├── media
│   ├── math/footnotes
│   └── mermaid
└── Obsidian adapter
    ├── documented variables
    ├── verified DOM selectors
    └── justified !important rules

Результат
└── один детерминированно собранный callmered-current.css
```

### Почему это не искажает предпочтения пользователя

Система не обязана выводить абстрактное описание вроде «стиль тёплый и информационно акцентный». Фактами остаются конкретная картинка, реакция, предыдущий CSS и новая картинка.

Модульность нужна только для того, чтобы:

- не потерять уже принятые детали;
- точно знать, какой фрагмент изменился;
- применять решение ко всем релевантным документам;
- отменять изменение одного компонента;
- собирать один действующий stylesheet.

## Предлагаемый протокол следующей CSS-итерации

1. Определить активную раскраску и её компонентный модуль.
2. Сохранить Markdown, скриншот и текущую собранную версию CSS.
3. Передать LLM:
   - дословную реакцию;
   - изображение или измеренное состояние текущей раскраски;
   - текущий модуль;
   - необходимые глобальные tokens;
   - неизменяемые интерфейсы соседних модулей.
4. Получить структурированное изменение одного модуля.
5. Проверить синтаксис и безопасность.
6. Проверить, что другие модули не изменились.
7. Собрать полный CSS программой.
8. Проверить обязательные селекторы и токены.
9. Применить CSS.
10. Снять новый скриншот.
11. Показать результат пользователю.
12. Сохранить всю цепочку как один факт итерации.

Для глобального запроса вроде «увеличить радиусы у всех поверхностей» разрешается менять token layer и автоматически получать изменения нескольких компонентов. Но список затронутых модулей должен вычисляться по ссылкам на токен, а не переписываться LLM вручную.

## Рекомендуемый порядок исправлений

### P0. Восстановить целостность текущего CSS

1. Взять последнюю полную версию перед регрессией.
2. Перенести в неё новую синтаксическую палитру.
3. Сравнить восстановленный CSS с обеими исходными версиями.
4. Проверить в обзорной статье:
   - список;
   - task list;
   - blockquote;
   - одну выноску;
   - таблицу;
   - code block;
   - изображение;
   - сноску.
5. Затем проверить подробные раскраски списков, выносок, кода и сносок.

### P1. Защитить стиль от повторной потери

1. Ввести компонентное внутреннее хранение.
2. Собирать полный CSS детерминированно.
3. Запретить локальному запросу менять несвязанные модули.
4. Добавить проверку обязательного покрытия.
5. Реагировать на аномальное уменьшение результата до применения.

### P2. Нормализовать токены без визуального редизайна

1. Развести raw, semantic и component tokens.
2. Сделать шрифты и основной размер единственными источниками истины.
3. Развязать page gutter и callout geometry.
4. Зафиксировать собственные радиусы.
5. Отделить общую геометрию inline-элементов от их типографики.

На этом этапе внешний вид должен измениться минимально: работа направлена на сохранность уже принятого решения.

### P3. Довести реальное компонентное покрытие

В таком порядке:

1. Таблицы.
2. Формулы.
3. Изображения и embeds.
4. Mermaid.
5. Интерактивные состояния.

Обзорная статья после каждого шага остаётся интеграционной проверкой.

### P4. Проверить читаемость и адаптивность визуально

1. Тёмная палитра кода — особенно red и purple.
2. H2 и другие элементы цвета `#b0ae9c`.
3. Unresolved links.
4. Inline code на green.
5. Узкое окно Obsidian.
6. Широкое окно Obsidian.
7. Многострочные заголовки.
8. Длинные таблицы, код и формулы.

Числа контраста используются только как сигнал для подготовки вариантов. Окончательное решение принимается по показанной раскраске и реакции пользователя.

### P5. Сократить интеграционную хрупкость

1. Убрать лишние дублирующиеся DOM-селекторы после проверки рабочего варианта.
2. Снизить число `!important`.
3. Разнести стабильные собственные tokens и версионно-зависимые детали Obsidian.
4. Добавить скриншотные проверки ключевых модулей.

## Критерии готовности системного исправления

Исправление можно считать законченным, когда выполняются все условия:

- текущий активный CSS снова содержит все принятые компоненты;
- последняя кодовая палитра сохранена;
- изменение одного компонента не меняет текст других CSS-модулей;
- полный CSS собирается программой, а не восстанавливается LLM по памяти;
- для каждого модуля есть минимальный структурный контракт;
- обзорная длинная статья показывает по одному базовому примеру каждого элемента;
- специализированные раскраски подробно проверяют каждый компонент в контексте статьи;
- шрифты, цвета, размеры, радиусы и интервалы имеют однозначные источники истины;
- page gutter не зависит от callout icon;
- на последнем скриншоте нет случайного горизонтального scrollbar;
- новые настройки кода не могут удалить списки, callouts или footnotes;
- откат способен отменить одну визуальную итерацию, не разрушая историю фактов.

## Решения, которые нельзя принимать автоматически

Следующие вопросы требуют новой картинки и реакции пользователя:

1. Должен ли `mark` действительно быть моноширинным.
2. Нужно ли различать hover, visited и обычную ссылку.
3. Допустимы ли более светлые surface-варианты red и purple внутри тёмного code block.
4. Является ли низкий контраст H2 намеренным.
5. Как должен выглядеть unresolved link, если текущий цвет слишком слаб.
6. Должны ли H3–H6 использовать единый line-height.
7. Как соотносятся базовый радиус 4 px и увеличенный радиус inline-элементов.
8. Какой должна быть максимальная ширина текстовой колонки.
9. Должны ли Mermaid-диаграммы иметь светлую поверхность статьи или отдельную поверхность.
10. Нужны ли таблицам заметные границы, заливка заголовка или только типографическое разделение.

Эти вопросы не следует задавать пользователю списком в текстовом виде. Каждый из них лучше превращать в конкретную визуальную итерацию соответствующей раскраски.
